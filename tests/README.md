# What these tests establish

## Native engine 0.9 validation

The independent runtime has its own numerical/storage/protocol tests, separate
from the compatibility-engine tests below. The ordinary fixtures remain
untrained. A new original `fixtures/tiny-qwen38.gguf` (423,808 bytes) exercises
four hybrid layers, HC, PLE, QSA, routed/shared experts and varied projections.
It is generated by `tests/new_qwen38_parity.rs`; it is not pretrained data.
SHA-256: `5a1b2d1d014100404d39f461dc8853e6919d5710422529aa8ca563cd2b29d837`.

```bash
cargo test --locked --offline -p forge-engine --lib
cargo test --locked --offline --test new_engine_parity --test new_quant_parity --test new_qwen38_parity
cargo build --release --locked -p forge-engine
python3 scripts/validate-forge-engine.py --binary target/release/forge-engine
python3 scripts/validate-native-api.py --binary target/release/forge-engine --output artifacts/native-api-local.json
```

Explicit Vulkan tests are ignored in ordinary test runs. On a configured Vulkan
device, `FORGE_VULKAN_TEST=1` enables their intentionally explicit software-device
opt-in. Set `VK_DRIVER_FILES` to the intended ICD when multiple drivers exist.

```bash
FORGE_VULKAN_TEST=1 cargo test --locked --offline -p forge-engine --lib vulkan::tests -- --ignored --nocapture
FORGE_VULKAN_TEST=1 cargo test --locked --offline --test new_qwen38_parity vulkan -- --ignored --nocapture
```

Consult the test functions for their exact opt-in environment variable and the
current `VALIDATION.md` for executed commands. Software Vulkan verifies packed
kernels, graph/state arithmetic, capacity pressure and synchronization. It is
not RX 9070 XT throughput or trained-model accuracy. The resident Qwen traces
compare every logit, normalized hidden vector, KV, recurrent state, raw indexer
key and PLE history against a separate numerical reference. Interleaved requests,
reset, prefill and numerical-error recovery are covered.

The native HTTP harness executes actual synthetic inference, not mock replies.
It checks JSON/SSE, tools, context, prefix reuse, replacement rollback, one/four
active requests, bounded queue overflow, queued/active cancellation and timeout.
The external-template gate takes a separately supplied official template and
compares rendered bytes against Python Jinja with Transformers JSON defaults;
Jinja2 is a test-only Python dependency. No model files are downloaded by tests.

Regenerate the original Qwen fixture without GPU execution:

```bash
FORGE_QWEN38_FIXTURE_OUTPUT=tests/fixtures/tiny-qwen38.gguf cargo test --test new_qwen38_parity hybrid_hyper_ple_qsa_shared_moe_f32_full_trace
```

## Compatibility engine history

The following describes tests introduced for the older application commands.
Their claims and concurrency limits do not describe the native 0.9 engine.

The fixtures are deterministic, **untrained synthetic models** generated entirely
by `scripts/make_tiny_fixture.py`. Both have a genuine one-layer transformer,
nonzero F32 weights, a 32-dimensional hidden state and a full byte-level
tokenizer. Their output projection deliberately selects the token `A`. They
test inference wiring, not language quality or speed.

| Fixture | Purpose | Size |
| --- | --- | --- |
| `fixtures/tiny-qwen3moe.gguf` | Four nonidentical experts, top-2 routing; used by the MoE-only frontend and HTTP tests | 188,256 bytes |
| `fixtures/tiny-qwen3.gguf` | Original dense reference; lower-level inference and negative policy tests | 113,696 bytes |

MoE SHA-256:
`a5c3df3b15a2d24017176a8d5ff742c5d8ca537aef599933bf2d6147392deba7`

Dense SHA-256:
`590d4f40f753f947cdd7e2750d178d092116f441e94701e010138625a478cf69`

To regenerate the MoE fixture without replacing the dense reference:

```sh
python3 scripts/make_tiny_fixture.py --moe tests/fixtures/tiny-qwen3moe.gguf
```

Run the Rust checks:

```sh
cargo test --locked
```

The complete modified-scope Rust regression command is:

```sh
cargo test --locked --workspace --lib --bins --test inference --test model_switch --test serve --test ops
```

The integration tests open the committed model with the actual RustingStrata
reader, build its tokenizer, run CPU forward passes, check finite logits and
changing hidden states, verify attention KV state, decode the expected output,
round-trip Unicode and reject a truncated tensor file.
The MoE test changes the active expert count from two to one and verifies that
the actual hidden state changes. This establishes executed expert routing;
the deliberately constant output token alone would not establish that.

Run the executable and HTTP checks after building:

```sh
cargo build --locked
python tests/smoke.py --binary target/debug/forge9070
```

On Windows, use `target/debug/forge9070.exe` instead. The standard-library-only
Python harness starts the executable on an ephemeral loopback port, then verifies
real CPU generation, server readiness, API-key enforcement, model listing,
OpenAI-compatible nonstreaming responses and SSE streaming, the configured
completion cap, and rejection of an invalid request. It terminates only the
server process it started. The chat requests set
`chat_template_kwargs.enable_thinking` to `false` so that the fixture's output
appears in `content`; the upstream default can put output in `reasoning_content`.

From 0.6, an explicit request over the completion cap is rejected before
inference rather than silently clamped. The dedicated
`scripts/validate-code-context.py` harness additionally checks coding presets,
repository selection/token budgets, exact chat-budget preview, context/model
limits, and unchanged active state after failed requests. See the current
validation record for the commands actually run.

## Request scheduling and coding API (0.7)

The unit suite covers the model-aware auto policy and admission controller,
including FIFO reservations, exact expiry boundaries, cancellation races,
capacity shrink/recovery and permit cleanup. Run the API template regressions
alongside the unit suites:

```sh
cargo test --locked --workspace --lib --bins --test serve --offline
python tests/scheduling_api.py --binary target/debug/forge9070
python tests/api-coding-client.py --binary target/debug/forge9070
node scripts/validate-code-ui-helpers.cjs
```

The scheduling test expands the existing untrained fixture in a temporary
directory and performs actual CPU decoding while it observes overload,
timeout, FIFO and cancellation through HTTP. The API test uses synthetic
checkpoints, including one deliberately emitting a complete function-call
token, to exercise JSON/SSE tool-call serialization and the next tool-result
turn. These establish transport and scheduler behavior, not real-model tool
selection, GPU concurrency, Qwen answer quality or token rates. Both scripts
clean their processes and sockets and save scope-labelled JSON evidence.

UI checks execute actual helper source in Node with minimal stubs. They do
not render the browser layout. No four-sequence Qwen GPU support was added.

## Model management and WSL launchers

The vendored `model_switch` integration test derives a second checkpoint from
the same fixture with a different output projection. It loads two models with
the same basename in separate catalogue directories and verifies actual output
changes from `AAAA` to `BBBB`. It also covers unload/reload, rejection of stale
model IDs, API authorization, catalogue containment and keeping the old model
when metadata preflight rejects a replacement.
Dense models are excluded from the catalogue and rejected by direct load calls,
including attempts to bypass the browser. Unsupported CPU parallel settings
also fail before unloading the current model.

Hugging Face unit tests use an actual local HTTP fixture server. They exercise
revision pinning, shard grouping, streaming downloads, range resume/restart,
size/hash validation, redirect authorization, provenance and proxy selection.
Header probes also cover real metadata policy enforcement, byte-range handling,
bounded reads and rejection of malformed/unsupported models. Compatibility
tests exercise routed expert geometry, custom unsupported quantizations and
standalone MTP head geometry. Correct shape does not prove a head was trained
for the same checkpoint.
They do not require a Hugging Face token or download a pretrained checkpoint.

On Linux, run the native launcher and CLI end to end:

```sh
python3 tests/models_cli.py --binary target/debug/forge9070
python3 tests/concurrency_cli.py --binary target/debug/forge9070
python3 tests/bench_cli.py --binary target/debug/forge9070
python3 scripts/test-wsl.py
```

`models_cli.py` executes the real native Linux launcher and CPU server, checks
nested catalogue IDs with spaces, switches/queries models, exercises stale-ID
errors and unload/reload, then stops the process it started. `test-wsl.py` uses
mock executables to check WSL/Windows argument conversion, explicit backend
selection, GPU preflight failure, directory precedence and token forwarding.
The mocks do not establish actual Windows interoperability or GPU execution.

## Concurrency and performance accounting

`concurrency_cli.py` runs four overlapping HTTP clients, including two SSE
streams, against real CPU inference. It checks isolated complete replies,
exact request/token accounting, bounded admission, disconnect recovery and the
concurrency benchmark's actual-token accounting with excluded warmup. CPU mode
correctly reports one compute slot: concurrent connections are served through
serial CPU generation. This test does not exercise GPU parallel compute.

Unit tests separately cover the optional expert-tail omission policy, model and
shard cache identities, calibration configuration matching and runtime benchmark
annotations. Policy tests do not establish GPU numerical behaviour or answer
quality under approximation. `scripts/bench-concurrency.py` is a measurement
tool for the user's running server, not a source of hardware performance claims
from the synthetic fixture.

These checks **do not** establish RX 9070 XT GPU correctness, performance,
large-model behaviour, quantized-kernel correctness, GPU MoE expert-cache behaviour,
or ROCm compatibility. Those require separate tests on the target machine with
appropriate supported model weights.

## Version 0.4 fidelity checks

CPU sampler tests reject empty and mixed non-finite logits while existing
sampling-distribution checks remain covered by the `ops` integration suite.
Pure tests exercise the shared GPU verification-input preparation, including
current RoPE positions, batch/context bounds and overflow. These tests do not
execute QSA or other GPU kernels.

The compatibility tests report actual low-bit tensor elements and routed expert
subsets, without assigning a model quality score. API tests reject non-neutral
unsupported sampling options instead of silently ignoring them, and reject
numbers that overflow the sampler's f32 representation.

Tuning tests check paired token/time accounting, excluded warmup, invalid or
missing samples, output-comparison eligibility and the improvement threshold.
The executable `bench_cli.py` harness checks four things with real CPU MoE
inference: the requested execution settings, excluded warmup and actual output
counts, paired per-run rates and their summaries, and recorded prompt/checkpoint
identities. It does not perform GPU calibration or evaluate a pretrained model.
The concurrency harness additionally changes KV settings through the real
management API while retaining the same model ID, then verifies that the
benchmark's configuration snapshot detects the change. CPU backend use means
this checks configuration tracking, not a GPU precision comparison.
# Independent engine validation in 0.8

`cargo test --locked -p forge-engine --lib` runs the independent loader,
quantization, SIMD, math, model-state, tokenizer and measurement unit tests.
`cargo test --locked --test new_engine_parity` compares all logits, normalized
hidden states and KV values against the compatibility engine, including dense
and MoE models with five storage formats and grouped-query attention. The
compatibility engine is a test oracle, not a dependency of `forge-engine`.

After building both release binaries:

```bash
python3 scripts/validate-forge-engine.py --binary target/release/forge-engine --frontend target/release/forge9070 --output artifacts/forge-engine-cli-0.8.0.json
target/release/forge-engine kernel-bench --json-out artifacts/native-kernels-0.8.0.json
```

These checks do not establish pretrained-model quality, native Vulkan,
Qwen3.8 execution or RX9070XT throughput. See `docs/NATIVE-ENGINE.md`.
